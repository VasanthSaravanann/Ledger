v2 pilot · one requisition · initial screen only

Manually sent, machine-enforced.

Ledger is Rust tooling for the audit-grade candidate feedback pilot in V2.md: 100% of rejected candidates on one high-volume requisition get a human-recorded reason, with no ATS integration and no automated decision.

  • Locked form

    GATE, FIELD, ADMIN — nothing else. No free text, no “Other”, no “skills mismatch”. A named decision maker and a capture timestamp on every row; corrections supersede, never overwrite.

  • Immutable log

    Every send carries the full rendered body and its hash, chained to the previous line. Edits and truncation are detected before the next send.

  • Three circuit-breakers

    Completeness, gate consistency, and version resolution. A form answer that contradicts the candidate’s own ATS answer blocks the send and escalates — it is never auto-corrected.

What the plan’s tasks became

The constraints live in the type system and the logs, not in a review checklist.
Task Enforcement
2.2 Tier 0 gate copy Five Australian knockouts, each with requirement, what satisfies it, and waivable / time-limited status — unusable until HM and Legal sign off.
2.3 Comparative paragraph One static paragraph per requisition; merge slots are rejected, so the same text goes to every candidate.
2.4 Master templates Allow-listed slots only. The only candidate-level value is the name, so the copy cannot be tailored per person.
3.2 Send log Exact rendered subject and body, plus the disposition capture time, chained and re-verifiable with ledger log verify.
4.2 Metrics Reply volume per 1,000 sends, form-block rate, and recorded criteria feasibility.

Run it

cargo build --release

ledger init --data pilot
ledger governance set --data pilot --escalation-owner "M. Okafor, Employee Relations"
ledger gate approve      --data pilot --actor "J. Chen"   --role hiring-manager
ledger templates approve --data pilot --actor "M. Okafor" --role legal
ledger playbook approve  --data pilot --actor "M. Okafor" --role legal

ledger requisition create --data pilot --id REQ-2026-014 \
  --employer "Example Health" --title "Registered Nurse" \
  --reply-to careers-feedback@example.com.au \
  --sender-name "R. Patel" --sender-title "Recruitment Coordinator" \
  --gate right-to-work --gate work-rights-duration \
  --fact ROLE_END_OR_MIN_TERM="30 June 2027" \
  --fact MIN_TERM="12 months" \
  --fact ROLE_DURATION_REASON="Fixed-term 12-month contract."

ledger ats import --data pilot --requisition REQ-2026-014 --file export.csv
ledger disposition record --data pilot --requisition REQ-2026-014 \
  --application APP-1001 --first-name Ada --email ada@example.com \
  --recruiter rec-rui --decision-maker dm-chen \
  --category GATE --gate work-rights-duration --answer shorter-than-role
ledger dispatch --data pilot --requisition REQ-2026-014 --preview
ledger qa record --data pilot --requisition REQ-2026-014 --application APP-1001 --qa qa-patel
ledger dispatch --data pilot --requisition REQ-2026-014
ledger log verify --data pilot
ledger metrics --data pilot --requisition REQ-2026-014

Metrics and routing

Pre-registered bands; the routing reads them, it does not score them.
Metric Green Amber Red
Reply volume< 30 / 1k30–80> 80
Form-block rate< 10%10–25%> 25%
Gate-mismatch rate< 2%2–10%> 10%
Criteria feasibilityyes, 1 sessionyes, external inputno
Candidate-value signal> 50% yes30–50%< 30%

The routing rule

  1. Candidate-value red → stop. Do not build v2.
  2. Gate-mismatch red → flag live discrimination exposure immediately.
  3. Form-block red → capture-discipline middleware is the v2 signal.
  4. Form-block green + criteria yes → reassess venture viability.
  5. Reply volume red → scope automated reply triage into v2.
  6. Criteria no → pivot to criteria-validation tooling.

The tool renders the exact text, applies the three circuit-breakers, and records the send. It never sends email and never calls the ATS — per the pilot’s scope, dispatch stays manual.

The constraints live in the type system, the lint, and the logs.
Task Enforcement
2.1 Locked form Three options, named recruiter and decision maker, append-only capture, and SUPERSEDES corrections that keep the original on file.
2.2 Gate blocks GATE-01–GATE-05 are versioned. A gate whose requisition facts are undocumented cannot be captured — the row must be recorded as FIELD.
2.3 Role-level paragraph Elicited into five slots, then rejected at sign-off for relative superiority, implied deficit, subjective proxies, or a years-of-experience bar.
2.4 Templates Template A/B/C with allow-listed slots, a fixed paragraph declining individual feedback, and three one-click value signals.
3.1 ATS filter Rows past the initial screen are dropped at import, so an interviewed candidate can never receive Template B.
4.1 QA runbook 100% of GATE emails and a deterministic 10% of FIELD/ADMIN need a recorded second-person check before dispatch.
4.2–4.3 Metrics and routing Five pre-registered green/amber/red bands, and the six V2 consequences applied in order.

The go / no-go rule

  1. Criteria not agreed by HM and Legal → criteria-validation consulting, whatever the metrics say.
  2. Criteria agreed and both rates inside policy (≤ 20 replies per 1,000 sends, ≤ 25% blocked) → v2 engineering.
  3. Criteria agreed but a threshold breached → hold and iterate on the manual pipeline.
