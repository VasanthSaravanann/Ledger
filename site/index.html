Three steps, and each one can refuse

The pilot's constraints are not a policy document. They are validation that rejects a bad row, a lint that rejects bad copy, and files that cannot be quietly rewritten.

1

Capture a reason

GATE, FIELD or ADMIN — nothing else. No free text, no “Other”. A named decision maker, a timestamp, and an Ed25519 signature. Corrections supersede; they never overwrite.

2

Gate the send

No disposition, no email. A gate answer that contradicts the candidate's own ATS answer blocks and escalates — it is never auto-corrected. A GATE email also needs a second-person QA check.

3

Prove what was sent

Every send is one line, chained by SHA-256 to the line before it, holding the exact rendered body. Edit one byte and the log refuses to load — and refuses to grow.

For the people who get asked afterwards

Three audiences, three surfaces, one source of truth.

  • HR and Legal read the three emails as candidates receive them, and see the four drafts the copy linter refused.
  • Recruiters work the triage queue: pending, GATE, FIELD, ADMIN, with a live preview before anything is committed.
  • Auditors verify the chain, the signatures, and the operator activity without write access.

And what it refuses to do

Stated plainly, because the omissions are the design.

  • No LLM in the send path. A person selects; the system renders.
  • No email sending. It renders the draft, records it as queued, and leaves delivery to your mail client.
  • No ATS API. One CSV in, one draft batch out.
  • No hosted service. The workspace is a directory your team holds.
  • No Windows binary. macOS and Linux only, tested.

Install and run it

Rust 1.85+. There is no published release yet, so build from source; the demo fixture needs no employer data. 

git clone https://github.com/VasanthSaravanann/Ledger
cd Ledger
cargo build --release

# deterministic fixture: 150 applicants, 147 sends, 3 blocks
./target/release/ledger demo seed --data pilot --force --record
./target/release/ledger log verify --data pilot
./verify_log.py pilot/send_log.jsonl   # stdlib-only, independent
tests 136 clippy -D warnings MSRV 1.85 verified zero network crates Windows unsupported

The recruiter workspace is an optional feature, so the default build stays a CLI: 

cargo build --release --features ui
ledger --data pilot --operator rec-rui ui --port 8420
# http://127.0.0.1:8420/?token=<one-time>

Questions people actually ask

Is this an AI tool?

No. There is no model in the send path: a human selects one of three reasons, and the system renders pre-approved text. The pilot exists to find out whether that manual pipeline is affordable — the five metrics decide whether v2 gets any automation.

Where does the candidate data live?

In a directory you choose, with the directory at 0700 and every state file at 0600. There is no server to leak. The workspace ships with a deterministic synthetic fixture so you can try it without touching real applicants.

What stops someone rewriting the log?

Nothing local. The chain proves internal consistency, not provenance: with write access you can fabricate a consistent log. The threat model says so, and the control is to publish the head hash off-host — ledger anchor writes a receipt you copy elsewhere.

Can I use it for my own requisition?

That is the intent, but read the format spec and the threat model first, and have your legal counsel confirm the privacy position for your jurisdiction. The tool records sign-off; it cannot give you one.
