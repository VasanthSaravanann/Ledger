# Contributing

## Supported platforms

macOS (aarch64, x86_64) and Linux (glibc) are supported and tested in CI. Windows is
**not** supported: no one has run this on Windows, and publishing an untested
cross-compiled binary is worse than publishing none.

## Before you push

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --locked
cargo test --locked --features ui     # exercises the web workspace
cargo clippy --all-targets -- -D warnings          # core must build without ui
cargo clippy --all-targets --all-features -- -D warnings
./verify_log.py /tmp/pilot/send_log.jsonl   # after `ledger demo seed --data /tmp/pilot --record`
```

## Lints and the `expect` policy

`clippy::unwrap_used`, `clippy::panic` and `clippy::indexing_slicing` are denied
crate-wide; tests are exempt via `clippy.toml`. `clippy::expect_used` is
deliberately **not** denied. `expect` is allowed only where the value is a
compile-time constant, and each such site carries a comment saying why it cannot
fail:

| Site | Why it cannot fail |
| --- | --- |
| `gate::GateLibrary::seed` | `"v1.0"` matches the version grammar |
| `demo::base_time` | fixed literal date, single-valued |
| `digest::truncate_to_seconds` | `with_nanosecond(0)` is valid for every instant |

If a proposed change adds an `expect` that is not in that table, it needs a
fallible API or a real error path instead.

## Coverage floors

`coverage-floors.toml` sets per-module line floors for the modules where a wrong
byte is expensive: `digest`, `log`, `pipeline`, `metrics`, `qa`, `template`.

| Module | Floor | Why this number |
| --- | --- | --- |
| `digest` | 80 | baselined, then five points below measured |
| `log` | 70 | IO error branches are hard to reach without fault injection |
| `pipeline` | 65 | the remaining paths are template/log errors already covered in their own modules |
| `metrics` | 75 | band boundaries are all covered; the gap is `Display` formatting |
| `qa` | 80 | baseline |
| `template` | 58 | the gap is `Display`/`Debug` and error formatting |

A floor may be lowered only in the same change that documents why here, and it
must never drop below the level that lets a validation regression through. Raise
a floor when you add tests; do not lower one to make a red build green.

## The chrono advisory

`cargo-deny` reports `RUSTSEC-2026-0543` (`chrono` unmaintained). `deny.toml`
ignores it with a reason and a review date (2026-12-31). `chrono` has no known
vulnerability; the ignore exists because migrating to `jiff` touches every
timestamp path and should be a scheduled change, not an incident. Do not extend
the ignore without recording why here.

## Format changes

`FORMAT_SPEC.md` is normative and `tests/golden.rs` pins it byte-for-byte. Any
change to the digest payload, the canonical encoding, or the fixture is a
`digest_version` bump: regenerate with `./scripts/build-site.sh`, update the
golden constants and the spec **in the same commit**, and re-run
`verify_log.py`.

## Site pages and provenance

`site/index.html` is hand-written (the product page). Every other page under
`site/` is generated by `./scripts/build-site.sh` from a real CLI run — the
workspace snapshots included, which is why that script builds with `--features ui`
and drives a live server. CI fails if committed output differs from a fresh
generation, so do not edit generated pages by hand. The snapshots must not render
timestamps, or the drift check would never pass.

Provenance (build SHA, generation time) is read from the committed
`site/provenance.json`, not from `HEAD`, so regeneration is byte-identical for a
fixed checkout. When you change the pages, bump it in the same commit:

```bash
LEDGER_BUMP_PROVENANCE=1 ./scripts/build-site.sh
git add site/ && git commit -m "regenerate site"
```

Vercel serves the committed pages through the GitHub integration; there is no
deploy-side Rust build. CI's drift check is what guarantees the deployed bytes are
the reviewed bytes.
