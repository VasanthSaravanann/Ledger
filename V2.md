**Scope:** Single pilot employer, single high-volume requisition (150+ applicants), initial screen stage only, 100% of rejected candidates. Zero ATS API integration or LLM inference in the send path.

## Phase 2: Build Core Artefacts (No-Code / Form & Copy Setup)

- [ ] **Task 2.1: Build the Single-Screen Disposition Form (Airtable / Microsoft Forms)**
  - **Action:** Build the locked disposition capture form (prefer Airtable for native conditional logic and record locking).
  - **Schema & Validation Rules:**
    1. `APPLICATION_ID` (Short text, Mandatory, Primary key — must match ATS export exactly).
    2. `REQ_ID` (Single select, Mandatory — pre-populated with pilot requisition ID only).
    3. `RECRUITER_ID` (Single select, Mandatory — named individuals only, no generic team names).
    4. `DECISION_MAKER_ID` (Single select, Mandatory — named person who actually made the adverse-action call, for *Barclay* contemporaneous state-of-mind traceability).
    5. `DISPOSITION` (Single select, Mandatory — **strictly 3 options**, no free text, no `"Other"`, no `"Skills mismatch"`):
       - `GATE` — Candidate's own application answers show they do not meet a stated mandatory requirement for this role.
       - `FIELD` — Candidate met the stated requirements. Not progressed because other applicants presented a stronger case. No individual deficiency identified.
       - `ADMIN` — Not progressed for a reason unrelated to this candidate (requisition withdrawn, rescoped, internal or redeployed hire).
    6. `GATE_CODE` (Single select, Conditional — visible and mandatory **only** when `DISPOSITION = GATE`; restricted to knockout codes active on the pilot req).
    7. `CAPTURE_TIMESTAMP` (Created time — automatic, read-only).
    8. `LOCKED` (Checkbox + field permissions — auto-locked on submit; zero post-submit edits).
    9. `SUPERSEDES` (Linked record — populated only when submitting a correction record).
- [ ] **Task 2.2: Configure Versioned Gate-Text Library (`GATE-01` to `GATE-05`)**
  - **Action:** Load the five pre-approved Tier 0 deterministic gate blocks with immutable `TEXT_VERSION` tags (e.g., `GATE-01-v1.0`). Mid-pilot edits require incrementing to `v1.1`.
  - **Blocks & Compliance Checks:**
    - `GATE-01` (**Right to work**): Strictly Australian work rights; never citizenship preference or national origin.
    - `GATE-02` (**Work-rights duration vs role duration**): Replaces "visa type"; requires `{{ROLE_END_OR_MIN_TERM}}`, `{{MIN_TERM}}`, and `{{ROLE_DURATION_REASON}}` documented in the requisition *before* posting (otherwise default to `FIELD`).
    - `GATE-03` (**Mandatory registration or accreditation**): Legislated registrations only (e.g., AHPRA, teacher registration, WWCC, licensed trades); personally verify `{{REGULATOR_URL}}` before launch.
    - `GATE-04` (**Licence**): Must include a signed-off `{{INHERENT_REQUIREMENT_REASON}}` tied to concrete duties (e.g., unaccompanied multi-site travel with no public transport); remove gate if HM/Legal cannot justify it.
    - `GATE-05` (**Location and work location requirements**): Must include `{{LOCATION_REQUIREMENT}}`, `{{CANDIDATE_LOCATION_ANSWER}}`, `{{LOCATION_SATISFACTION_TEXT}}`, `{{WAIVER_TEXT}}`, and the mandatory record-correction invitation.
- [ ] **Task 2.3: Elicit & Sign Off Role-Level Comparative Paragraph (`FIELD` Copy)**
  - **Action:** Interview the Hiring Manager before the req opens using the 4 verbatim elicitation questions:
    1. What did all shortlisted applicants demonstrate that most applicants did not?
    2. What concrete evidence proved it (project, metric, tool, scale)?
    3. What did a strong application make visible within 30 seconds?
    4. What did many applicants assume mattered that actually didn't?
  - **Drafting & Audit Rules:**
    - Populate `{{ATTRIBUTE_1}}`, `{{ATTRIBUTE_2}}`, `{{ATTRIBUTE_3}}`, `{{EVIDENCE_PATTERN}}`, and `{{NON_FACTORS}}`.
    - **Reject at sign-off** if text contains: relative superiority claims (*"more experience than most"*), implied deficits (*"candidates typically lacked..."*), subjective proxies (*"cultural fit"*, *"right attitude"*), undisclosed criteria not in the PD, or years-of-experience bars.
- [ ] **Task 2.4: Configure Master Email Templates (`Template A`, `Template B`, `Template C`) & Candidate-Value Signal**
  - **Action:** Set up the three mail-merge templates with named sender details (`{{SENDER_NAME}}`, `{{SENDER_TITLE}}`, `{{EMPLOYER}}`) and human reply-to notice:
    - **Template A (`GATE`):** Renders `{{GATE_TEXT_BLOCK}}` + record-correction invitation.
    - **Template B (`FIELD`):** States candidate met stated requirements with zero individual shortfall + renders `{{ROLE_LEVEL_PARAGRAPH}}` + retains explicit paragraph declining individual feedback + `{{REENGAGEMENT_LINE}}`.
    - **Template C (`ADMIN`):** Renders one of three exact pre-approved strings (`requisition withdrawn`, `role rescoped and will be re-advertised`, or `filled internally or by redeployment`) + `{{REENGAGEMENT_LINE}}`.
  - **Instrument Candidate-Value Signal:** Embed one-click feedback links (`Yes` / `Somewhat` / `No` for *"Was this useful for your next application?"*) via three `mailto:` links or a no-free-text single-question form.
- [ ] **Task 2.5: Set Up the 5-Scenario Canned Reply Playbook**
  - **Action:** Save pre-approved reply macros in the monitored mailbox for the coordinator:
    1. *"Please give me individual feedback"* -> Decline plainly; restate no individual shortfall was identified; point to role-level paragraph.
    2. *"You recorded my answer wrongly"* -> Audit ATS record; if erroneous, log a `SUPERSEDES` correction record, fix record, and reinstate if req is open (APP accuracy compliance).
    3. *"What should I do differently next time?"* -> Restate role-level paragraph + general application guidance only.
    4. *"I think this was discriminatory"* -> Do not argue merits; acknowledge within **1 business day** and escalate immediately to named ER/Legal owner.
    5. *"Can you keep me in mind for other roles?"* -> Send pre-approved re-engagement line and talent-pool consent link.

## Phase 3: Build Data Schemas, Validation Script & Immutable Send Log

- [ ] **Task 3.1: Define ATS CSV Export & Hard Stage Filter**
  - **Action:** Configure the ATS export view with minimum required columns:
    `APPLICATION_ID, FIRST_NAME, EMAIL, REQ_ID, ROLE_TITLE, STAGE_AT_REJECTION, KO_ANSWER_01..KO_ANSWER_n, APPLIED_DATE`
  - **Guardrail:** Hard-filter `STAGE_AT_REJECTION` to **initial screen only** so interviewed candidates never receive Template B.
- [ ] **Task 3.2: Provision the Append-Only Immutable Send Log**
  - **Action:** Create the master send log spreadsheet/table restricted to append-only access for one non-recruiter administrator.
  - **Required Columns:**
    `SEND_ID, APPLICATION_ID, REQ_ID, DISPOSITION, GATE_CODE, DECISION_MAKER_ID, CAPTURE_TIMESTAMP, SEND_TIMESTAMP, TEMPLATE_ID, TEXT_VERSION, RENDERED_BODY_HASH, RENDERED_BODY_FULL, DELIVERY_STATUS, REPLY_RECEIVED_FLAG`
  - **Guardrail:** Persist `RENDERED_BODY_FULL` verbatim alongside `RENDERED_BODY_HASH` for tribunal evidentiary sufficiency.
- [ ] **Task 3.3: Build Local Validation & Merge Script (Agent Coding Task)**
  - **Action:** Write a local CLI script (Python/Rust) that ingests the ATS CSV export and Disposition Form CSV export, performs a left join on `APPLICATION_ID`, and enforces the three hard circuit-breakers before generating mail-merge output:
    1. **Disposition Completeness Check:** Block any ATS row lacking a locked disposition record; increment `form_block_count` and return to `DECISION_MAKER_ID`.
    2. **Gate Consistency Check:** For `DISPOSITION = GATE`, verify `GATE_CODE` matches the candidate's `KO_ANSWER_xx` in the ATS export. Block and escalate mismatches to the coordinator (never auto-correct).
    3. **Version Resolution Check:** Verify every `FIELD` row resolves to the signed-off `ROLE_LEVEL_PARAGRAPH` version for `REQ_ID`.
  - **Output:** Generates clean mail-merge CSV + appends entries (with SHA-256 hash and full rendered body) to the Immutable Send Log.

## Phase 4: Pilot Execution & Pre-Registered Threshold Evaluation

- [ ] **Task 4.1: Enforce Operational Dispatch Runbook**
  - **Action:** Execute bulk rejections for the 150+ applicant requisition following the mandatory sequence:
    1. Recruiter/Decision-Maker completes Disposition Form **before** changing ATS status.
    2. Export ATS CSV (initial screen filter applied) and run local validation/merge script.
    3. Coordinator performs second-person QA check on **100% of `GATE` emails** and a **10% random sample** of `FIELD`/`ADMIN` emails.
    4. Dispatch via mail merge and commit entries to the Immutable Send Log.
- [ ] **Task 4.2: Track Pre-Registered Instrumentation Metrics**
  - **Action:** Compute the five decision metrics at pilot close against pre-committed thresholds:

| Metric | Definition | Green | Amber | Red |
| :--- | :--- | :--- | :--- | :--- |
| **Reply volume** | Replies per 1,000 sends | `< 30` | `30–80` | `> 80` |
| **Form-block rate** | Blocked sends ÷ attempted sends | `< 10%` | `10–25%` | `> 25%` |
| **Gate-mismatch rate** | `GATE` records failing KO consistency check | `< 2%` | `2–10%` | `> 10%` |
| **Criteria feasibility** | HM + Legal approve structured criteria + inherent-requirement justification? | Yes (1 session) | Yes (external input) | No |
| **Candidate-value signal** | One-click `"Yes"` share on usefulness prompt | `> 50%` | `30–50%` | `< 30%` |

- [ ] **Task 4.3: Execute v2 Go/No-Go Routing Decision**
  - **Action:** Route v2 product scope strictly based on empirical pilot readings:
    - **Candidate-value signal Red (`< 30%`):** Stop — do not build v2.
    - **Form-block rate Red (`> 25%`):** Strongest v2 signal — build v2 around capture-discipline middleware.
    - **Form-block rate Green + Criteria feasibility Yes:** Thin middleware risk — reassess venture viability.
    - **Reply volume Red (`> 80/1,000`):** Scope automated reply triage into v2 core architecture.
    - **Gate-mismatch rate Red (`> 10%`):** Flag live discrimination exposure to employer immediately; package knockout-audit diagnostic.
    - **Criteria feasibility No:** Pivot v2 to criteria-validation tooling/consulting with feedback dispatch as its output layer.
